# Korean / Japanese / Chinese Anki Pipeline

## Overview

This project generates Anki flashcards for Korean, Japanese, and Chinese vocabulary
with proper field separation — each card has dedicated fields for Expression,
Meaning/Reading, Nuance, and 3× Example sentences (each with EN translation,
and JA translation when relevant).

Sentences are generated via LLM (DeepSeek V4 Flash, ~$0.09/110 words) using
the `delegate_task` subagent system.

---

## Pipeline: Korean Vocab (Complete)

### Source

- **Korean_Vocabulary_by_Evita.apkg** — a community Anki deck with 6,500
  frequency-ordered Korean words. Download from AnkiWeb (search "Korean
  Vocabulary by Evita"). Contains hangul, English, hanja, and audio files.

### Data flow

```
Evita .apkg
  │
  ├── Extract 6,500 notes via SQLite → fields: Korean, English, Hanja, Audio
  │
  ├── Generate sentences via LLM → batches of ~200 words
  │   Each batch: subagent generates 3× (Korean sentence, Japanese, English)
  │   Format: ===word: 학교===
  │           학교에 가요.
  │           学校に行きます。
  │           I go to school.
  │           (blank line)
  │           (next sentence...)
  │
  └── Build .apkg via genanki → 14-field model:
        Korean, English, Hanja, Audio, Nuance,
        Example1, Example1_JA, Example1_EN,
        Example2, Example2_JA, Example2_EN,
        Example3, Example3_JA, Example3_EN
```

### Key files

| File | Purpose |
|------|---------|
| `data/raw/nikl_vocab.tsv` | NIKL TOPIK vocabulary (secondary source, used for cross-check) |
| `data/processed/sentences_clean.txt` | First 110 words' sentences (manual batch) |
| `data/sentences_raw/batches_output/batch_*.txt` | All 32 batch outputs |
| `src/20_build_test_deck.py` | Test deck builder (100-110 cards) |
| `src/40_build_final.py` | Final 6,500-card deck builder |
| `src/10_build_nikl.py` | Abandoned NIKL-based approach (kept for reference) |

### Pipeline scripts

**20_build_test_deck.py** — Builds a limited card set for testing.
Usage: `DECK_SIZE=500 python3 src/20_build_test_deck.py [count]`
Reads Evita .apkg, merges sentences from sentences_clean.txt, outputs .apkg.

**40_build_final.py** — Builds the full 6,500-card deck.
Reads Evita .apkg, reads all batch output files, builds .apkg with media.
Parses two sentence formats: `===word: X===` and `## X (definition)`.

### Sentence generation

Sentences were generated by dispatching `delegate_task` calls with batches of
~200 words. Each delegate task:
1. Receives context about the learner (beginner Korean, N1 Japanese)
2. Generates 3 simple Korean sentences per word (해요체 polite form)
3. Translates each to natural Japanese and simple English
4. Writes output to a file in strict format

Cost: ~$0.08 per 500-card batch (100 words × 3 sentences).
Wall time: ~2-3 minutes per batch with 3 concurrent subagents.

## Pipeline: Chinese Vocab (Planned)

### Current state (legacy)

- **Chinese deck: 15,189 cards** — 3-field note type: Expression, Meaning, Reading
- **Chinese WIP: 1,183 cards** — new cards from Pleco auto-insert, pending AI processing
- Note type: Basic `Chinese` with fields `Expression | Meaning | Reading`

### Source

- **Pleco dictionary app** — user looks up words, Pleco auto-inserts into
  "Chinese WIP" deck via Anki integration. Format: Expression (simplified
  Chinese), Meaning (Pleco HTML with definitions, pinyin, part of speech),
  Reading (pinyin).

### Workflow (current, manual)

1. Word lands in "Chinese WIP" automatically from Pleco
2. User copies word to DeepSeek online with prompt:
   "For each Mandarin word, give translation, nuance, then 3 example sentences with EN translations"
3. User pastes result back into the card body (dumped into Meaning field as HTML)
4. User manually moves card from "Chinese WIP" → "Chinese"

### Workflow (target)

1. **Create new note type** `Chinese Enhanced` with fields:
   `Expression | Meaning | Reading | Nuance | Example1 | Example1_EN |
    Example2 | Example2_EN | Example3 | Example3_EN`

2. **Extract WIP + deck cards preserving scheduling:**
   - Read cards from old note type
   - Create new notes under new type
   - Copy scheduling data (interval, ease, due, reps, lapses) to new cards
   - For cards with existing rich Meaning field: attempt to parse out
     old examples/nuance if present
   - For fresh WIP cards: LLM generates Nuance + 3 EN example sentences

3. **Batch generate** via delegate_task similar to Korean pipeline:
   - Context: "Chinese learner (near-native Mandarin level)..."
   - Prompt: "For each Chinese word: Translation, Nuance paragraph,
     3 example sentences in Chinese with English translations"
   - Output: structured fields ready for Anki

### Scheduling transfer mechanism

Review history lives on **cards**, not notes. When building a new .apkg:

```python
# Read old card scheduling
old_card = conn.execute("""
    SELECT type, queue, due, ivl, factor, reps, lapses, odue, odid
    FROM cards WHERE nid = ?
""", (old_note_id,)).fetchone()

# Create new card with same scheduling
new_card = {"type": old_card[0], "queue": old_card[1], "due": old_card[2],
            "ivl": old_card[3], "factor": old_card[4], "reps": old_card[5],
            "lapses": old_card[6], "odue": old_card[7], "odid": old_card[8]}

# genanki's Card model doesn't expose low-level scheduling, so we
# inject directly into the SQLite db.
```

### Card export with scheduling

Anki's .apkg is a zip containing `collection.anki2` (SQLite). To preserve
history: build the database directly with genanki, then patch the `cards`
table to set scheduling columns before zipping.

Alternatively: export the original cards as-is (with history), then
create a **mirror** deck under the new note type. The user reviews the
new deck, and old cards retire naturally.

3. User copies word to DeepSeek online for nuance + examples
4. User pastes result back into card body
5. User moves from "Japanese WIP" → "Japanese"

1. **Create new note type** `Japanese Enhanced` with fields:
   `Expression | Meaning | Reading | Nuance | Example1 | Example1_EN |
    Example2 | Example2_EN | Example3 | Example3_EN`

2. **Import Takoboto cards directly** into Japanese WIP with correct fields:
   - Takoboto.Japanese → Japanese_Enhanced.Expression
   - Takoboto.Reading → Japanese_Enhanced.Reading
   - Takoboto.Meaning → Japanese_Enhanced.Meaning
   - Takoboto.Sentence → Japanese_Enhanced.Example1 (if exists)
   - Skip reverse cards (we can add them as separate card template later)

3. **Deduplication**: check all Japanese deck cards before importing. If
   Expression already exists, skip (don't re-add).

4. **Batch generate** similar to Chinese pipeline:
   - Context: "Japanese learner (N1 level)..."
   - Just nuance + 3 Japanese examples with EN translations
   - No Chinese/other languages (user is N1)

## Common Pitfalls

1. **Homographs in kengdic**: kengdic lists slang/offensive homograph entries.
   Fix: prefer entries with hanja field (indicates Sino-Korean origin).

2. **Sentence format fragility**: subagent output must use strict format.
   The `===word: X===` header tripped up early versions. Enforce in prompt.

3. **genanki field count**: Model and Note field counts must match exactly,
   including empty fields. Mismatch raises ValueError.

4. **Media extraction**: Evita uses numeric filenames (0.mp3, 1.mp3...) mapped
   via a `media` JSON file. Must extract and include all in the .apkg.

5. **FSRS retention**: Set per-deck, not per-note-type. Import first, then
   configure deck options. Reschedule not needed for new cards.

6. **WIP vs main deck migration**: New cards should go into a WIP deck first
   for batch generation, then move to main deck once enhanced.

### Scheduling preservation code sketch

```python
import zipfile, sqlite3, genanki
from pathlib import Path

# Read old card scheduling
old_conn = sqlite3.connect("old.db")
old_data = old_conn.execute("""
    SELECT n.flds, c.ivl, c.reps, c.lapses, c.queue, c.type, c.due, c.factor, c.odue, c.odid
    FROM cards c JOIN notes n ON c.nid = n.id
    WHERE c.did = ?
""", (old_deck_id,)).fetchall()

# Build new deck with genanki
# ... then patch scheduling into the SQLite:
new_conn = sqlite3.connect("new.db")
for old_row, new_note_id in zip(old_data, new_note_ids):
    new_conn.execute("""
        UPDATE cards SET ivl=?, reps=?, lapses=?, queue=?, type=?, due=?, factor=?
        WHERE nid = ?
    """, (old_row[1], old_row[2], old_row[3], old_row[4], old_row[5],
          old_row[6], old_row[7], new_note_id))
new_conn.commit()
```

This is safe because we're only touching the `cards` table — the `notes` table
(where the content lives) is freshly built with the new note type.
